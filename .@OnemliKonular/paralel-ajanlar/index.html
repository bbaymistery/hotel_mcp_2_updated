0 · Böyük şəkil: mətbəx bənzətməsi

Bir restoran mətbəxi təsəvvür et. 4 aşpaz (ajan) eyni anda işləyir. Bunun qaydasında getməsi üçün 4 şey lazımdır:

Ayrı masaHər aşpazın öz kəsmə taxtası var, bir-birinin yeməyinə toxunmurlar.
= git worktree
Sifariş kartı"2 porsiya plov, duzsuz, 20 dəqiqəyə". Qısa və aydın.
= ticket
Divardakı qaydalar"Əlləri yu, ət ayrı taxtada, menyu belədir". Hər aşpaz gələndə oxuyur.
= CLAUDE.md / AGENTS.md
Gecə növbəsiSən evdəsən, amma xəmir hazırlanır. Səhər yoxlayırsan.
= background, /loop

Sən isə baş aşpazsan: kartları yazırsan, işi bölürsən, sonda hər yeməyi dadıb (code review) masaya buraxırsan (merge). İş elanının əsl soruşduğu budur: "Ajanları idarə edə bilirsənmi?"

Antigravity-də etdiyin ilə fərqAntigravity-də bir ajana dizaynı, digərinə API inteqrasiyasını vermək düzgün məntiqdir. Əlavə olunan yalnız budur: hər ajan öz qovluğunda, öz branch-ında işləyir (worktree), işi yazılı kartla alır (ticket) və "bitdi" deyəndə testlər bunu sübut edir.

1 · Git worktree: hər ajana ayrı masa

Problem: iki ajan eyni qovluqda

Hər iki ajanı hootel-booking-mcp-server qovluğunda işə saldın:

  • Ajan A (dizayn) client/src/components/RoomCard.tsx-ı yarıya qədər dəyişib.
  • Ajan B (API) həmin anda npm test işlədir. Testlər A-nın yarımçıq kodunu görür və qırmızı olur. B səhvi özündə axtarmağa başlayır, amma səhv onda deyil.
  • B öz işini commit edir. git add . A-nın yarımçıq fayllarını da commit-ə qatır.
  • Biri git checkout ilə branch dəyişsə, hər ikisinin altındakı fayllar dəyişir.

Yəni bir qovluq = bir masa. İki aşpaz bir masada işləyəndə bir-birinə mane olur.

Həll: worktree

Əvvəlcə iki anlayışı ayıraq:

BranchVersiyanın xətti, tarixçədəki ad. Görünmür, sadəcə git-in içində bir göstəricidir.
WorktreeO branch-ın diskdə ayrıca qovluğu. İçində bütün fayllar var, açıb redaktə edə bilərsən.

Normalda 1 repo = 1 qovluq = eyni anda 1 branch. Worktree ilə 1 repo = bir neçə qovluq, hər birində fərqli branch, eyni anda. .git tarixçəsi ortaqdır, yəni repo-nu təkrar klonlamırsan. Sadəcə əlavə "iş masaları" açırsan.

Əsas qovluqhootel-booking-mcp-server\
branch: main
← sən buradasan
Ajan A: dizaynhootel-booking-mcp-server-wt-design\
branch: agent/design
Ajan B: webhookhootel-booking-mcp-server-wt-webhook\
branch: agent/webhook
Hamısı eyni .git tarixçəsini paylaşır. Bir qovluqda commit edilən o biri qovluqda dərhal git log agent/... ilə görünür.

Əmrlər

# yeni masa aç: yeni branch + yeni qovluq, main-dən başlayır
git worktree add -b agent/design ..\hootel-booking-mcp-server-wt-design main

# hansı masalar var?
git worktree list

# iş bitdi, merge etdin → masanı yığışdır
git worktree remove ..\hootel-booking-mcp-server-wt-design
git branch -d agent/design

Sənin claude-kit-ində bunu bir əmrlə edən hazır skript var: claude-kit/scripts/new-worktree.ps1. O, worktree açır, .env-i ora kopyalayır (çünki .env git-də yoxdur) və nə edəcəyini yazır:

.\.@OnemliKonular\claude-kit\scripts\new-worktree.ps1 design
.\.@OnemliKonular\claude-kit\scripts\new-worktree.ps1 webhook
# bitəndə:
.\.@OnemliKonular\claude-kit\scripts\new-worktree.ps1 design -Remove

VS Code-da necə görünür

  1. Hər worktree qovluğunu ayrı VS Code pəncərəsində aç: code ..\hootel-booking-mcp-server-wt-design.
  2. Hər pəncərədə Claude Code panelini aç (və ya terminalda claude yaz). Hər ajan yalnız öz qovluğunu görür.
  3. Hər worktree-də bir dəfə npm install et, çünki node_modules git-də yoxdur.
  4. İki ajan eyni anda server işə salırsa, portlar toqquşur (hər ikisi 3001 istəyir). Birində $env:PORT=3002 ver.
Claude Code-un öz worktree dəstəyiClaude Code özü də sessiyanı ayrıca worktree-də aça bilir: terminalda claude -w design (və ya claude --worktree design). Bu, skriptsiz ən qısa yoldur. Bir fərq var: kit-dəki skript .env-i mütləq kopyalayır. -w ilə açanda isə yeni qovluqda .env olub-olmadığını yoxla, yoxdursa əl ilə kopyala.

İş bitəndə: masadan mətbəxə

agent/design branch→ sən diff-i oxuyursan →Pull Request / git merge→main→worktree remove
Toqquşmanın qarşısını ticket alırWorktree işləyərkən mane olmağın qarşısını alır. Amma iki ajan eyni faylı dəyişibsə, merge zamanı conflict yenə çıxacaq. Ona görə işi əvvəlcədən fərqli fayllara bölürsən. Bunu ticket-in "Scope" bölməsi edir (növbəti bölmə).

2 · Ticket formatı: qısa və aydın iş kartı

Ticket bir iş tapşırığının yazılı kartıdır. Jira, Linear və GitHub Issues-dakı "task" ilə eyni şeydir. Ajan üçün ticket-in xüsusi qaydaları var:

  • Kiçik: bir ajan bir sessiyada bitirə bilsin (1–3 fayl kod + testlər).
  • Aydın: ajan "nə istəyirdi görəsən" deyə təxmin etməsin.
  • Yoxlanıla bilən: "bitdi"nin mənası testlə ölçülsün.
  • Sərhədli: hansı fayllara toxunacağı və hansılara toxunmayacağı yazılsın. Paralel ajanlar bu sayədə bir-birinin faylına girmir.

"Webhook-u yaxşılaşdır."

Nəyi yaxşılaşdırım? Hansı faylı? Nə vaxt bitmiş sayılır? Ajan ya çox az edəcək, ya da yarım layihəni yenidən yazacaq.

✓ Yaxşı

Aşağıdakı kart: məqsəd, sərhəd, hər biri testlə bağlı qəbul şərtləri və yoxlama əmrləri.

# 001 — Webhook retry worker

**Type:** feature
**Branch / worktree:** agent/webhook-retry

## Goal
Uğursuz webhook-lar indi yalnız server restart olanda yenidən göndərilir.
Hər 10 saniyədə PENDING event-ləri yoxlayan bir worker əlavə et.

## Scope
- Toxunulacaq: `src/services/webhook.service.ts`, `src/api/server.ts`,
  `tests/integration/outbox-lifecycle.test.ts`
- Toxunulmayacaq: `client/`, `prisma/migrations/`

## Acceptance criteria (hər biri bir test)
- [ ] Given next_retry_at keçmiş PENDING event, when worker işləyir,
      then event DELIVERED olur → tests/integration/outbox-lifecycle.test.ts
- [ ] Given next_retry_at gələcəkdə, when worker işləyir,
      then event toxunulmaz qalır → eyni fayl
- [ ] Given server dayanır, then worker interval təmizlənir (leak yoxdur)

## Verify
- npx tsc --noEmit
- npx vitest run tests/integration/outbox-lifecycle.test.ts

Bu şablon artıq səndə var: claude-kit/project/tickets/TEMPLATE.md. Kit-dəki /ticket əmri isə bir cümlədən belə bir kart yaradır:

/ticket webhook uğursuz olanda periodik retry worker

"Given / When / Then" quruluşu belə oxunur: Given başlanğıc vəziyyətdir, When baş verən hadisədir, Then gözlənilən nəticədir. Hər sətir birbaşa bir testə çevrilir.

4 · Gecə işi: background, /loop, /schedule

Elan "ajanların gecə də işləyə bildiyini göstər" deyir. Bunun mənası belədir: sən kompüterdən uzaqda olanda iş davam edir, səhər isə yoxlanmış nəticəni görürsən. Bunun üç yolu var, sadədən mürəkkəbə:

a) Background: "sən başqa işlə məşğul ol, mən bunu görürəm"

Claude Code uzun bir işi (testlər, build, alt-ajan) arxa planda işlədə bilir. Sən eyni vaxtda başqa şey soruşursan, iş bitəndə xəbər gəlir. Sadəcə belə yaz: "bunu background-da işə sal". Ən sadə forma isə bu səhifədə gördüyün worktree-lərdir: 3 terminal, 3 ajan, hamısı eyni anda işləyir.

b) /loop: "bunu hər X dəqiqədən bir təkrarla"

/loop Claude Code-un bir əmridir. Verdiyin tapşırığı müəyyən intervalla təkrar-təkrar işə salır. Saatlı zəngli saat kimi düşün: hər dəfə çalanda ajan oyanır, tapşırığı yerinə yetirir və yenidən gözləməyə keçir.

# hər 30 dəqiqədən bir: testləri işə sal, qırmızı varsa düzəlt
/loop 30m npm test işlət; qırmızı test varsa səbəbini tap və düzəlt, commit et

# hər 15 dəqiqədən bir: PR-ı yoxla, CI qırmızıdırsa düzəlt
/loop 15m açıq PR-ın CI nəticəsinə bax, uğursuzdursa düzəlt və push et

# interval verməsən, ajan tempi özü seçir
/loop tickets/ qovluğundakı növbəti ticket-i götür, bitir, testləri yaşıl et
/loop-un şərtiLokal işləyir: kompüter və Claude Code sessiyası açıq qalmalıdır. Kompüteri söndürsən, loop da dayanır. Gecə üçün ya kompüteri açıq qoyursan, ya da (c) bəndinə keçirsən.

c) /schedule: buludda, kompüter sönülü olsa belə

/schedule bulud tapşırığı yaradır. Ajan Anthropic-in serverində, cədvəllə (cron) işə düşür. Məsələn: "Hər gecə saat 02:00-da testləri işlət, sınanları düzəlt, PR aç." Kompüterin sönülü ola bilər. Səhər GitHub-da PR görürsən.

Gecə ajanının qızıl qaydası: ajana nəzarətsiz merge icazəsi verməSəhər oyananda main-də yoxlanmamış kod görmək istəmirsən. Ona görə gecə ajanı:
  • ticket ilə işləyir (nə edəcəyi yazılıdır),
  • öz worktree / branch-ında işləyir (main-ə toxunmur),
  • testlər yaşıl olmadan "bitdi" deyə bilmir. Sənin kit-dəki Stop hook (verify.mjs) bunu məcburi edir,
  • sonda yalnız PR açır. Merge-i səhər sən edirsən.

5 · Hamısı birlikdə: bir iş günü

  1. Səhər, 15 dəqiqə: 3 ticket yaz (/ticket ...). Hər birinin "Scope" bölməsində fərqli fayllar olsun.
  2. 3 worktree aç: new-worktree.ps1 design, webhook, ab-test.

  4. Ajan "bitdi" deyəndə: Stop hook tsc + test işlədir. Qırmızıdırsa ajan dayana bilmir və düzəltməyə davam edir.

  6. Sən: diff-i oxuyursan və merge edirsən. Qərar və məsuliyyət səndədir.
  7. Axşam: qalan ticket-lər üçün /loop və ya /schedule qurursan. Səhər PR-ları yoxlayırsan.

7 · Müsahibədə necə danışmaq

"Paralel ajanları necə işlədirsən?"
"Hər ajan öz git worktree-sində, öz branch-ında işləyir. Belə olanda bir-birinin yarımçıq kodunu görmürlər. İşi əvvəlcədən fayl sərhədləri olan kiçik ticket-lərə bölürəm, ona görə merge conflict demək olar ki, olmur. Hamısı eyni CLAUDE.md qaydalarını oxuyur."
"Ajanın 'bitdi' dediyinə necə inanırsan?"
"İnanmıram, yoxlayıram. Hər ticket-in qəbul şərtləri testlə bağlıdır. Stop hook typecheck və testləri işlətmədən ajanı dayanmağa qoymur. Sonra kodu başqa bir model (Codex/Gemini) review edir. Son qərar isə mənimdir."
"Gecə işi?"
"Lokal təkrarlanan işlər üçün /loop, kompüter sönülü olanda /schedule ilə bulud tapşırığı. Gecə ajanı heç vaxt main-ə merge etmir, yalnız PR açır. Səhər mən review edirəm."
